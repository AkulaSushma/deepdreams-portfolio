The repository is organized as a product portfolio rather than a single application: each invitation variant lives in its own top-level directory plus a legacy `_previous-design` tree, all served from the same root. Every product exposes the same public URL shape `/invite/:slug`, which is routed by platform configs — `vercel.json` rewrites it to `/api/invite?slug=:slug`, while `netlify.toml` redirects it to `/.netlify/functions/invite` — so the identical Node.js handlers under `api/` run unchanged on either platform. The `api/` layer (invite, publish preflight/recover, admin login/tokens/site, cron keepalive) persists data to Supabase via `supabase/schema.sql` and is consumed by both the static frontends and the shared browser runtime under `shared/` (`hydrate.js`, `image-prep.js`, `publish-client.js`). A single `admin/index.html` console talks to the same admin routes for every product. Root-level scripts (`_audit.js`, `_optimize-images.js`, `_weight.js`, `capture-*.js`, `scratch-*.js`) are one-off tooling reused across products during development, and `loadtest/k6` scripts target the staging deployment to validate concurrency and caching claims across the whole portfolio.
